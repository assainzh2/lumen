# ADR-002: Content comes from a server pipeline and ships as signed packs

**Status:** Draft
**Date:** 2026-10-08
**Deciders:** Assain
**Supersedes (in part):** ADR-001, the distribution and storage parts only. Its product rules still apply.

## Context

ADR-001 uses `content.json` for retrieving data (fully offline on the phone). `content.json` is limited to its initial values. Whenever I want to add more facts or change something, I have to edit `content.json` manually, which requires a new app build. I want new data to appear automatically from a server. Also, every item should have a real source and not be a fake fact or citation. Other constraints stay the same: the widget works fully offline at runtime, app users never log in, and the repo is public.

## Decision

1. We will fetch texts from chosen websites or books and store each with its URL. Content comes from these sources, never from an LLM's memory.
2. Our LLM runs on the server, in `apps/worker`, never on the phone. It turns a text into one widget item and must attach the quote and the URL as its source, to reduce hallucination.
3. We will verify each item automatically: the quote must appear word for word in the stored source text. This reduces hallucinations but does not eliminate them, so human review stays.
4. We drop duplicates using pgvector. Then I approve or reject each item in the admin dashboard. Only approved items can be published.
5. The approved items go into a **content pack**: a versioned file, a snapshot of the approved items. The server database (Postgres) is the source of truth, and the phone never queries it live. The server signs each pack with a private key and publishes the signature next to it.
6. The phone downloads the latest pack when it has a network, and checks the signature with a public key built into the app. If the check fails, it rejects the pack and keeps the last valid one. After a successful check it saves the pack, and the scheduler runs from the saved pack, fully offline.

**OPEN (to decide later, not silently):**
- Where the private signing key lives. It must never be in the repo.
- The signature algorithm. Candidate: CryptoKit's Curve25519 signing.
- ~~Where the phone stores the pack~~ **Resolved:** in the App Group container, shared by the app and the widget. On 2026-10-08, with Xcode 26.6 (17F113) and a free Personal Team, an iPhone app wrote a counter via `UserDefaults(suiteName:)` and the widget read the same value. App Groups therefore do not require the paid program. Still unverified: the 7-day expiry behavior.
- When the phone fetches: at app launch, on a schedule, or both.
- The pack format and versioning, including what happens to the shuffle when a new pack changes a pool size (SCHEDULER_SPEC open question 6).

## Options considered

| Option | Pro | Con | Verdict |
|---|---|---|---|
| App calls the API live without content packs | No need for data storage | I need widgets to work offline; too many API calls if I have more users in the future | Rejected |
| Keep bundling `content.json` (ADR-001) | Easy to implement | Needs manual updates and a new app build | Rejected as the main source |
| Server pipeline + signed packs (this ADR) | Offline at runtime; new content without an app build; a tampered pack is detected | A server to run, a key to protect, more moving parts | **Chosen** |

## Consequences

- **Easier:** we can add new content without shipping a new app every time.
- **Harder:**
  - *Running a server:* it costs money, and it can go down. The phone keeps the last valid pack, so a server outage must not break the widget.
  - *Protecting the signing key:* the private key is the only thing that makes a pack trusted. Whoever holds it can push anything to every phone. It must be kept outside the repo and be hard to steal.
  - *Pack versions:* each pack gets a version number. A new pack can change how many items a kind has, which changes the shuffle (the scheduler picks items by position in a shuffled pool). If this is not handled, the widget could repeat or skip items when a new pack arrives.
  - *Hallucinations that pass verification:* the automatic check only proves the quote exists in the source. It does not prove the LLM's summary is faithful to that quote. A wrong summary with a real quote passes, which is why human review stays.
- **Still open:** the OPEN list in Decision, and the open questions in `docs/SCHEDULER_SPEC.md`.
- **Future goal, not now:** reduce how much human review is needed. This is risky for the reason above, so any automation needs an eval (`packages/evals`) that shows it catches bad items.
